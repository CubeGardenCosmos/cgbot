## 待决策

### R6.1 微信入口

- 首期不支持微信；何时启动后置适配另行确认。身份关联流程、配对方式与陌生人处理仍待定，不把官方包的 DM `pairing` 策略直接定为新框架方案（§4、§12.1、§12.1c）。
- 协议无官方规格文档。调研基线为腾讯官方包 `@tencent-weixin/openclaw-weixin` 2.4.10 与 AstraBot `weixin_oc`；选用提取客户端、自写适配或参考其他实现，及版本复核方式待定。以官方行为为核对依据，不照搬 AstraBot 缺口（§12.1c）。
- 登录需覆盖调研记录的 `scaned/need_verifycode/scaned_but_redirect/binded_redirect` 状态；采用服务端 `longpolling_timeout_ms`、统一超时与本地二维码生成的具体方案待细化，不用第三方二维码服务泄露登录链接。错误码 `-14` 是暂停还是清空后重登，不能直接沿用任一参考实现的处理（§12.1c）。
- `bot_token`、`account_id`、`base_url`、`get_updates_buf`、每用户 `context_token` 必须持久化；存储与恢复细节待定。消息媒体使用 AES-128-ECB CDN，SILK 解码需自备；与语音链路的衔接待明确（§12.1c）。
- 主动发送依赖最近入站消息的 `context_token`；缺 token 时官方包虽发送请求，服务端是否接受未验证，AstraBot 则直接跳过。token 有效边界及主动通知可用性需实测，不能据此提前承诺微信通知能力（§12.1c）。

### R6.2 通知与统计

- 每日统计按近多少天、按何种消息计数，数据存哪里、谁负责写入；无统计、并列、统计失效时怎样选择入口，均待定。现有 `GroupStatistics` 只在群内发日报，并非“最常用入口”实现（§6、§11.7、§12.3.1）。
- 后台事件如何触发模型轮次是待细化接口；“系统事件入队”在 §6、§13.7 为推论，不把原 AstraBot `CronMessageEvent` 继续作为新框架约定。R1.7 收束后由本条接入（§6、§13.7）。
- 微信不可主动推送、无有效 token 或入口不可用时的通知处理与回退待定；微信通知回退随微信适配一并后置（§12.1、§12.1c）。

### R6.3 功能与数据迁移

- §8 末行功能逐项取舍及迁移优先级待定；人设/群聊/私聊提示词、句子拆分、Face/Reply、表情回应等旧输出规则是否保留也未全部确认。旧规则不因“可移植”而自动成为需求（§8、§11.6、§11.8、§12.3.4）。
- `group_messages` SQL/表结构可复用，历史数据是否导入新库待定；群技能卡 merge/format/parse 与提示词的采纳范围，以及插入顺序截断、子串 `LIKE` 误匹配的处置需明确。记忆本原来未实现，不存在可直接迁移的旧记忆库（§8、§11.7）。
- 试运行期间旧群聊分析与新闻订阅暂停；结束后恢复旧框架还是迁入新框架待定。该待答项不授权试运行时拉起 AstraBot，也不预设恢复并行运行（§12.2）。
- §8 对 dsh_caged 的旧复用描述由 §13.7 后续决议覆盖：彻底放弃 DSH，只复用无关基础组件；Codex 与 OMP 归 M5，不在本阶段重新讨论是否保留 DSH（§13.3、§13.7）。

### R6.4 切换与运行问题

- 部署位置已定为“暂不讨论”，不能据语音路径限制先指定同机部署；最终部署方式、共享路径等运行前置条件待后续收束（§11.3、§12.1）。
- 实测好友与固定群号在真实测试时再定；服务范围白名单的“范围外事件一律丢弃”为 §12.2 推论，需与 R1.1 收束，不能把全好友/全群试运行当成默认配置（§12.1–§12.2）。
- NapCat 多 WS 客户端行为仅有结构层面的推论，新增条目前仍需边界验证；地址、鉴权与连接参数沿 R0.1/R1.2 收束。现有 `astrbot:6199` 无对端按 30 秒间隔重连失败，不因此恢复旧框架（§9、§11.2、§12.1）。
- 硬编码 bearer token 与内部端点已被观察到；应轮换并迁入配置，新框架不得复制。轮换范围、执行主体、授权与完成证据待落实；本文不执行旧系统密钥变更，也不记录密钥值。管理员 QQ 硬编码与备份文件是否涉及所选迁移资产需核对，不能无审查照搬（§11.9）。
- 旧容器全部 Paused，暂停原因未知；保留现状。历史事件循环卡顿已观察到，但 `_watch_loop` 是推论原因，不作定论；所选监视逻辑的隔离、超时及不阻塞主循环方案在 M5 收束，并向上线验收交接（§11.1、§11.9、§13.7）。
- NapCat WebUI 暴露、compose token 权限及语音服务监听/UDS/路径约束问题已有观察；现有部署的处置方式与授权待定。SoVITS/ASR 服务端严禁修改、重启或改配置/venv；内网/UDS 访问、不外转路径参数，以及客户端并发和超时建议仍需在 M4/运行方案收束，不能借修复安全问题越过服务端禁改边界（§8、§11.2–§11.3、§11.9、§12.2）。

## 与其他阶段的接口

- [M0](M0-baseline.md)：收束 §12.3 中尚未回答的功能与统计问题，制定配置、密钥处理等工程约定；本阶段保留后置决策，不把 §12.3 已被后续决议回答的 DSH、微信首期范围等重新打开。
- [M1](M1-core.md)：提供配置白名单、统一消息模型、身份/入口、会话、回复工具和系统事件接口。多入口预留不等于首期实现微信；跨入口私聊仍为每用户一个总会话。
- [M2](M2-private-chat.md)、[M3](M3-group-chat.md)：试运行仅验收选定范围的已定行为；迁移旧功能不得恢复旧防抖/群聊触发规则，也不得让通知统计或迁移数据绕过私聊/群聊可见域隔离。微信仅私聊，不接 M3 群门控。
- [M4](M4-voice.md)：承接 ASR/TTS 客户端与媒体转换，不修改服务端；部署路径、可达性、并发与超时的未决项向 R6.4 交接。
- [M5](M5-coding-agent.md)：承接 Codex 替代 DSH、OMP 工具及回报桥接；后台完成通知经收束后的系统事件接口交给 R6.2，监视循环不得因复用重带历史卡顿问题。
- R6.4 的 QQ 受限试运行不以 R6.1 微信或全部旧功能迁移为前置；只在选定试运行范围的依赖满足且获必要授权后推进。当前仅文档规划，不改远端、不启动容器、不修改 NapCat 配置。

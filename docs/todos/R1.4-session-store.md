## 执行任务

- [ ] R1.4-T01：确认会话采用追加式记录和 SQLite 的方案，明确每用户私聊总会话、群会话与记忆本的存储职责，不擅自采纳 §12.1b 全部建议。
  - 进展:代码按主 Agent 转达的用户决定采用 SQLite(WAL,单库文件由调用方给定,记忆本后续在同库加表)。DESIGN §5.2 仍为推论,本条未由文档确认,故未勾选。
- [x] R1.4-T02：定义消息、工具调用、工具结果、压缩事件的记录契约与排序/引用关系，使恢复后能重建已确认的上下文结构（§5.2）。
  - 推论:记录 kind ∈ {user, assistant, tool_call, tool_result, system_event, compaction};`tool_call`/`tool_result` 必须带非空 `call_id`(工具结果经 `call_id` 关联调用);`tool_result.output` 必须为 str(与 Responses `function_call_output.output` 一致);`compaction` 必须带 str `summary`。排序由全库单调 `seq` 决定,会话内按 seq。
- [ ] R1.4-T03：确认摘要与近期尾部的引用方式、压缩前原记录保留和“仍落盘但不再送模型”的边界；压缩尾部策略交 R2.3，不在存储层定数量。
  - 进展:已实现"最近一次 compaction 及其后条目为活动窗口,之前条目保留在库中"。尾部保留方式未定:存储层不解释尾部;若 R2.3 需保留尾部原记录,推论做法是在压缩事件之后以新条目重新追加,或在 payload 中引用原 seq。待 R2.3 与用户确认,故未勾选。
- [x] R1.4-T04：定义持久化提交与重启恢复行为，区分已提交历史、未完成模型请求及已经外发的 reply；未完成轮次是否续跑/重放另作决定，不默认重复外发。
  - 实现:每次 append 独立提交(BEGIN IMMEDIATE…COMMIT,WAL,synchronous=FULL);未提交的 append 重启后不可见;存储层不保存"未完成轮次"状态,不做任何重放。未完成轮次的续跑/重放仍为待决策。
- [x] R1.4-T05：定义提供给 R1.6/R1.7 的读取、追加与活动时间交接，记录并发写入与恢复的约束；SQLite 路径、表结构与迁移策略待确认后细化。
  - 接口:`SessionStore`(同步)与 `AsyncSessionStore`(asyncio.to_thread 包装):`append(session_id, kind, payload) -> seq`、`load(session_id, after_seq=0)`、`load_active(session_id)`、`last_activity(session_id)`、`list_sessions()`、`close()`。并发:单连接 + threading.Lock 串行化进程内读写;跨进程写由 SQLite 写锁串行。
  - 推论:`last_activity` = 该会话最新一条记录的 ts(任意 kind 均计入);空闲口径待 R1.7/R2.3 确认。
  - 表结构(推论,待确认):`schema_version(component, version)`,会话组件 `component='session'`、版本 1,供记忆本等后续切片各自登记;`session_items(seq INTEGER PK AUTOINCREMENT, session_id, kind, payload TEXT JSON, ts REAL)`,索引 `(session_id, seq)`。库版本高于代码支持版本时拒绝打开。迁移策略尚无。
  - 工具输出截断/落盘(推论):`tool_result.output` 超过 `tool_output_limit`(默认 64 KiB,UTF-8 字节)时,行内保留前 limit 字节加标记,全文写入 `spill_dir`(默认 `<库目录>/spill`)的新文件,路径存入 `spilled_path`,另记 `original_bytes`。文件先 fsync 再提交行;若提交前崩溃,仅留孤立文件,不产生悬空引用。
  - 损坏记录(推论):读取时 payload 非 JSON 则抛 `SessionStoreError`,不跳过。

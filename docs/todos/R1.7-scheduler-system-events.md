## 待决策

- 推论：事件载荷为 `kind`（自由非空字符串）+ `user_id`（可空）+ JSON `payload` dict；约定 payload 不放消息正文，待 R1.6/R2.x 确认。
- 推论：交付为至少一次；handler 成功返回后才标记已交付，崩溃窗口内可能重复交付，消费方需按 `event_id` 幂等。
- 推论：严格按 `(due_at, 插入序)` 串行交付；失败的队首阻塞后续事件直到成功，长时间失败会拖住队列，是否改为可跳过需 R2.x 确认。
- 推论：无死信；失败按指数退避，上限 `retry_max_delay`（默认 300s）无限重试；是否设次数上限与告警待定。
- 推论：重启后超期事件立即交付、不丢弃；是否按 kind 设过期窗口（尤其后台通知）待定。
- 推论：handler 必须快速移交给会话派发，不能 await 整轮 Agent 运行，否则后续事件全部等待。
- 推论（R1.7-T04 未决）：同用户忙、输入等待、压缩中的合并与顺序规则未实现，归 R2.1/R2.2/R2.3；`reschedule` 仅对非运行中事件生效。
- 推论：`SystemEventQueue` 仅内存、无界、不持久，进程退出即丢失；仅用于可丢失的进程内通知，关键事件须走 `Scheduler`。
- 空闲活动定义、压缩与来信竞争归 R2.3（§5.4）；8 小时主动执行本身已定。
- 群主动触发的小时边界、时区由 M3 决定；通知最常用入口统计归 R6.2。
